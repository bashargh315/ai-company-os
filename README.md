# AI Company OS — v1.0 MVP

نسخة موحدة لمشروع AI Company OS، مخصصة لتشغيل أول عميل باشتراك مدفوع مع مساحة تهيئة مجانية قبل الدفع.

## v1.3 — حماية مسارات التنفيذ
- كل مسارات التنفيذ المدفوعة محمية على مستوى API، وليس فقط عبر أزرار الواجهة.
- تأكيد الدفع أصبح آمناً من التكرار؛ إعادة التأكيد لا تنشئ اشتراكاً ثانياً.
- لوحة المدير تتطلب صلاحية المالك على مسارات الإدارة.

## ما الذي أصبح جاهزاً
- مساحة عميل مستقلة ومساحة مدير مستقلة.
- تهيئة مساحة العميل بدون دفع، بينما التنفيذ والبحث والتقارير للعميل تتطلب اشتراكاً مدفوعاً.
- Company Brain مع نسبة فهم وأسئلة ناقصة.
- محادثة تحفظ في قاعدة البيانات.
- اختيار Agents حسب الطلب.
- بحث حي اختياري عبر Tavily؛ النظام لا يخترع مصادر عندما لا يكون البحث متصلاً.
- تقرير بحث أولي.
- تشغيل تجربة أولى ينتج خطة 7 أيام + حزمة محتوى + مؤشرات قياس.
- منع تكرار تشغيل نفس تجربة العميل خلال 24 ساعة عند تطابق الطلب.
- موافقات المدير قبل التواصل الخارجي الحساس.
- صفحة نتيجة للعميل مع تنزيل نصي.
- FastAPI + SQLite + Docker + Render.

## تشغيل محلي
```bash
python -m pip install -r requirements.txt
python run.py
```
ثم: `http://127.0.0.1:8000/app`

واجهة المدير: `http://127.0.0.1:8000/manager`
توثيق API: `http://127.0.0.1:8000/docs`

## إنشاء مساحة العميل
يمكن إنشاء مساحة العميل دون دفع لتهيئة الحساب واختيار الخطة. أما تنفيذ المهام والبحث والتقارير للعميل فلا تعمل إلا بعد تفعيل اشتراك مدفوع؛ الوصول الداخلي للمدير مجاني للاختبار.

## البحث الحي
ضع `TAVILY_API_KEY` في البيئة لتفعيل البحث الخارجي. بدون المفتاح تبقى وظائف الـMVP المحلية عاملة، لكن لا يتم ادعاء وجود بحث حي.

## المصادقة
النسخة الأولى تستخدم Demo User افتراضياً لتسريع تجربة أول عميل. أزرار Google/Facebook/X جاهزة للربط مع Supabase عندما تتم تهيئة OAuth. لا تستخدم النسخة الحالية OAuth كحماية إنتاجية نهائية.

## النشر
يوجد `Dockerfile` و`render.yaml`. النشر بالحاوية يتبع النمط الموثق لتطبيقات FastAPI.

## الحالة التجارية
هذه MVP قابلة للتجربة وليست منصة SaaS نهائية. قبل البيع الواسع يجب إضافة مصادقة إنتاجية، PostgreSQL، إدارة أسرار، حدود استخدام، دفع، سياسة خصوصية وشروط، اختبارات أمنية، ومراجعة تراخيص مزودي الذكاء الاصطناعي.

## v1.3 Payment layer
Customers request a paid plan. The backend creates a payment request; a configured checkout URL can be opened when available. Otherwise the manager can confirm receipt manually for testing.
